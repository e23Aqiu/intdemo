# 统信 UOS ARM64 应用内逐文件更新

## 1. 方案与版本边界

- 新协议：`uos-file-update-v2`。
- 新布局：`uos-file-layout-v2`，文件名为 `file-layout.json`。
- 平台：统信 UOS Desktop 20 Professional ARM64（`linux-aarch64`）。
- v1.2.2 的 `uos-layered-v1` 三层协议继续保留，只用于兼容已经发布的客户端和
  清单；新构建不再生成整层替换包。
- v1.2.4 完整 DEB 是首个逐文件基线。v1.2.3 没有 `file-layout.json`，所以
  v1.2.3 → v1.2.4 自动只发布完整 DEB；首个可发布的逐文件包是
  v1.2.4 → 后续版本。
- 旧整 DEB `uos-deb-xdelta-v1` 读取能力也继续保留，但新构建不再使用它。

## 2. 用户侧不变项

1. 用户首次安装仍只安装一个 DEB，不需要另装插件、Python、更新器或 root 常驻
   服务。
2. 后续更新仍在客户端内检查、下载和应用。逐文件条件不满足时自动下载完整 DEB，
   由系统安装器正常安装。
3. 完整 DEB 始终发布并保留，逐文件包只是可选优化，不是唯一恢复路径。
4. v1.1.0、v1.1.1 和所有未声明 `uos-file-update-v2` 的客户端不会看到新包，继续
   收到完整 DEB 或按定向策略收到 HTTP 204。
5. 更新协议不修改账号表、访问令牌、刷新令牌、设备授权、客户端数据库、凭据文件
   或同步协议，已有登录账号不会失效。

## 3. 完整 DEB 内的布局

```text
/opt/apps/com.e23aqiu.intdemo/files/
├── app/                     # 业务程序、Python/Qt 运行库和资源
├── browser/                 # 内置 Chromium
├── intdemo-client           # 稳定启动器，只随完整 DEB 更新
├── client-online.json       # 在线连接配置，只随完整 DEB 更新
├── certs/                   # HTTPS CA，只随完整 DEB 更新
├── layer-layout.json        # 旧三层兼容布局
└── file-layout.json         # 全部受管文件的类型、权限、大小和 SHA-256
```

`file-layout.json` 逐项记录 `app/` 和 `browser/` 下的普通文件与符号链接。稳定启动器、
在线配置和 CA 继续作为不可由应用内包替换的引导区，并写入统一引导指纹。

## 4. 补丁内容

构建器解开真实已发布来源 DEB，并按 `file-layout.json` 逐路径比较：

- 新增或内容、权限、类型发生变化的普通文件：写入 `.intlayer` 的 `payload/`；
- 新增或变化的符号链接：只写入目标布局，不携带外部文件；
- 目标版本已不存在的文件：写入 `deleted_paths`；
- 完全相同的文件：不进入更新包；
- Chromium 未变化时不会再次进入包。

包内只有唯一 `manifest.json` 和新增/变化的普通文件。目标完整布局、删除清单、来源
布局哈希和目标布局哈希都在清单中。它不对压缩后的 DEB 或 `data.tar` 做二进制差分。

以下情况自动只保留完整 DEB：

- 来源 DEB 没有 `file-layout.json`；
- 稳定启动器、在线配置或 CA 引导指纹发生变化；
- 受管文件没有任何变化；
- 逐文件包达到完整 DEB 的 50%；
- 来源 DEB、发布收据、目标 DEB、清单或回放校验不一致。

## 5. 客户端组装、删除与回滚

客户端先校验 HTTPS 下载的大小和 SHA-256，再执行：

1. 精确核对来源版本、来源布局哈希、目标版本和目标布局哈希。
2. 拒绝绝对路径、`..`、重复路径、未声明文件、特殊文件和越界符号链接。
3. 完整校验本机来源布局；本机基线缺失或被改动时立即回退完整 DEB。
4. 在用户数据目录的临时版本目录中创建目标文件树。
5. 新增/变化文件从包中解出；删除清单中的路径不进入新目录；未变化文件优先硬链接
   复用。DEB 种子由 root 所有、硬链接受限时使用只读种子链接；系统不支持链接时
   回退复制。
6. 对组装后的每个目标文件重新核对类型、权限、大小和 SHA-256，并同时校验旧三层
   兼容布局。
7. 全部匹配后原子安装目标版本目录并写入待试运行标记。
8. 用户点击“重启并应用”后，稳定启动器等待旧进程退出并试运行新版本。
9. 新版本显示登录界面并稳定进入 Qt 事件循环后确认成功；确认前退出时，下次启动
   自动回到上一个已确认版本或 DEB 种子。
10. 确认成功后只保留当前版本，清理旧版本及已使用的 `.intlayer` 下载文件。

```text
<get_data_dir()>/uos-layers/
├── downloads/               # 下载并通过 SHA-256 的逐文件包
├── versions/<版本>/         # 已完整组装和校验的用户级版本
├── pending-version          # 待试运行版本
├── pending-attempted        # 已尝试但尚未确认
└── current-version          # 当前已确认版本
```

该目录只保存程序文件，不保存或搬移 `client-v2.db`、账号凭据、访问/刷新令牌、在线
会话、用户配置、浏览器业务资料或同步数据。

## 6. 能力协商与服务端选择

新版 UOS 客户端发送：

```text
X-IntDemo-Update-Capabilities: uos-file-update-v2, uos-layered-v1, uos-deb-xdelta-v1
```

新清单示例：

```json
{
  "platforms": {
    "linux-aarch64": {
      "full": {
        "installer_path": "/updates/files/IntDemo-UOS-arm64-1.2.4.deb",
        "sha256": "<完整 DEB SHA-256>",
        "size": 327000000
      },
      "file_updates": [
        {
          "format": "uos-file-update-v2",
          "from_version": "1.2.3",
          "source_layout_sha256": "<v1.2.4 文件布局 SHA-256>",
          "target_layout_sha256": "<v1.2.4 文件布局 SHA-256>",
          "installer_path": "/updates/files/IntDemo-UOS-arm64-Files-1.2.3-to-1.2.4.intlayer",
          "sha256": "<逐文件包 SHA-256>",
          "size": 3000000,
          "target_sha256": "<完整 DEB SHA-256>",
          "target_size": 327000000
        }
      ]
    }
  }
}
```

服务器只在平台、精确 `from_version` 和 `uos-file-update-v2` 能力同时匹配时选择
逐文件包。没有新能力时会从顶层和平台节点移除 `file_updates`，再选择旧分层、旧
DEB 差分或完整 DEB。因此 v1.1.0/v1.1.1 的响应结构和安装行为保持原样。

## 7. UOS 构建、Windows 发布

来源版本为 `N`、目标版本为 `N+1` 时：

1. Windows 发布器填写“UOS 逐文件来源”为 `N`，点击“导出已发布基线包”。
2. 将 `uos-delta-base-N.zip` 带到 UOS ARM64 真机并导入。文件名沿用旧格式以兼容
   既有基线传递流程；包内仍是真实已发布 DEB 和 `publish-receipt.json`。
3. UOS 代码切到目标版本并构建。`build.sh` 生成完整 DEB、旧兼容布局和逐文件布局；
   `build-files.sh` 解开来源 DEB，生成逐文件包并在真机完整回放。
4. 来源没有新布局、引导区变化或包过大时，报告写入 `fallback_to_full=true`；结果
   ZIP 仍正常导出，只是不包含 `.intlayer`。
5. 将一个 `uos-build-result-*.zip` 带回 Windows，点击“导入统信构建包”。发布器会
   自动恢复来源版本并识别逐文件包或完整包回退，不需要单独导入裸补丁。
6. Windows 构建结果就绪后仍使用同一个“双端发布”按钮。发布器同时上传完整包和
   合格的可选补丁，并原子替换清单。

用户电脑不需要保存旧 `.deb` 文件；客户端使用当前安装种子或已确认版本目录作为
本机来源。构建机仍必须持有真实已发布来源 DEB 和发布收据，不能用重新构建的同版本
DEB 替代。

## 8. 发布门禁与部署顺序

逐文件候选必须同时满足：

- 来源 DEB 与来源发布收据的名称、大小、SHA-256 一致；
- 来源版本低于目标版本；
- 来源和目标逐文件布局自校验通过；
- 引导指纹一致；
- ARM64 真机回放后的完整目标目录与目标布局一致；
- 补丁严格小于目标完整 DEB 的 50%。

发布前发布器会检查 `/updates/capabilities.json` 是否声明
`uos-file-update-v2`。部署顺序必须是：

1. 先升级服务器。该变更只扩展匿名更新清单选择，不需要数据库迁移，不修改认证和
   会话，v1.1.0/v1.1.1 及已登录账号继续正常使用。
2. 验证旧客户端无能力头时只收到完整 DEB 或 HTTP 204。
3. 构建并发布 v1.2.4 完整 DEB，建立首个逐文件基线。即使来源填写 v1.2.3，
   也会因为旧 DEB 没有新布局而安全回退完整包。
4. 后续版本先在测试通道定向 v1.2.4，验证小包下载、文件删除、启动确认和回退。
5. 保留目标完整 DEB，灰度通过后再扩大允许更新的来源版本。

## 9. 验收清单

- 完整安装只需一个 DEB，无外部插件。
- v1.1.0/v1.1.1 仍使用完整包，已有登录状态不变。
- v1.2.3 → v1.2.4 是正常完整包回退，不报构建失败。
- v1.2.4 → 后续仅新增一个资源时，包内只有变化的业务文件和清单，不包含 Chromium。
- 删除目标文件后，回放目录中不再出现该文件。
- 来源文件被篡改、包损坏、布局不匹配或空间不足时自动使用完整 DEB。
- 待确认版本启动失败后回到已确认版本；确认成功后清理所有旧版本。
- 账号数据库、令牌和凭据路径在更新前后完全不变。
